# Task OIW-919: Database-level approval hardening (non-blank approver, append-only approvals)

## Owner
Claude Code lead (Opus orchestrator) with a Sonnet implementation worker. **Migration owner for the sprint.**

## Branch
`agent/claude/OIW-919-approval-db-hardening`

## Worktree
Isolated sibling worktree; location recorded in the lead session only.

## Objective
Make the database itself refuse an approval without a real approver and refuse any edit or ad-hoc deletion of a recorded Approval, so "the database enforces the human-approval gate" is true without qualification.

## Background
OIW-918 (PR #23, tests/security/approval-governance.test.ts) proved with raw SQL: (1) `approvals.approver` has only NOT NULL, so an empty-string approver row is accepted; (2) such a row satisfies the `decisions_require_human_approval` trigger (db/migrations/0000_dear_the_liberteens.sql ~L362-378), so a privileged SQL writer could approve a high-risk Decision with no human identity; (3) approvals are not append-only (UPDATE/DELETE allowed). The application exposes none of these paths. ADR-005 says an Approval is an immutable governance record. Legitimate deletions exist: workspace expiry (`packages/application/src/workspace-expiry.ts`, `scripts/expire-demo.ts`), demo reset/seed (`scripts/reset-demo.ts`, seed-reset integration tests), `pnpm db:reset`, and FK `ON DELETE cascade` from workspaces/decisions; tests use TRUNCATE ... CASCADE.

## Functional Requirements
1. CHECK constraint: approver must contain a non-whitespace character (`btrim(approver) <> ''`); also update the `decisions_require_human_approval` function so a qualifying Approval must have a non-blank approver (defence in depth).
2. Append-only: a trigger rejects every UPDATE on `approvals`; DELETE is rejected unless it is part of a whole-workspace or whole-decision cascade or an explicit, transaction-scoped purge (e.g. `SET LOCAL oiw.allow_governance_purge = 'on'` set only by the expiry/reset code paths). Choose the narrowest design that keeps expiry, reset, seed, `db:reset` and test TRUNCATE working; TRUNCATE does not fire row triggers (state it). Record the design and alternatives in ADR-013.
3. Check whether `audit_entries` is already append-only at the DB level (README claims "append-only audit trail"); if not, apply the same pattern in the same migration and ADR.
4. Tests on real Postgres: blank/whitespace approver rejected by CHECK; UPDATE rejected; ad-hoc DELETE rejected; workspace expiry, demo reset and decision cascade still succeed; existing approval-governance characterisation tests from OIW-918 that pinned the gaps are flipped to assert the new behaviour (coordinate: if PR #23 is not merged yet when you start, rebase on main after it merges — the lead merges it first).
5. Migration must be idempotent under `pnpm db:migrate` re-runs and apply cleanly to a database already holding demo data (the live Neon demo will receive it automatically via deploy.yml): verify by seeding a workspace with an approved decision on the old schema, then migrating.

## Non-Goals
Changing approval semantics in the UI or application, new contracts.

## Acceptance Criteria
1. All new and existing tests pass, including e2e reset/expiry paths.
2. Raw-SQL attempts from OIW-918 now fail at the database.
3. ADR-013 documents the purge escape hatch and its threat model.
