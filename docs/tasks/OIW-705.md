## Objective
The final Wave 3 deliverables (PRD §26 Wave 3): a pack authoring guide a
contributor can follow end to end, and a scaffold template pack that
passes `validate:packs` out of the box. Documentation + template content
only.

## Background
Three real packs run one core (common lifecycle 11/11); contracts v1.5;
the validator enforces manifests, observation/event/case/metric contracts,
checksum-keyed extractions and event-definition ambiguity. The guide must
teach what the three packs' history proved matters: contract-first
authoring (the OIW-004b/110/701 defect classes), the A1 checksum workflow,
value discriminators, and gold sets aligned to narrative semantics.

## Inputs
- `AGENTS.md`, PRD §11/§12/§21.2, `packages/contracts/src/configuration.ts`
  (+ observation/event/case/metric schemas), `packages/scenario-sdk/README.md`,

  `docs/agent-runs/OIW-004b.md`, `OIW-110.md`, `OIW-701.md` (defect classes
  to warn about), `docs/PLAN_AMENDMENTS.md` (A1/A2/A5/A7)

## Owned Paths
- `docs/PACK_AUTHORING.md` (the guide)
- `scenario-packs/_template/` (scaffold: manifest, labels, one entity/
  observation/event/case schema each, one workflow, one rule per rule
  file type, three dashboards using A5 widgets, one metric per aggregation

  minimal gold set, README) — must LOAD as a valid pack; prefix ids with
  `template-` and keep content industry-neutral (a generic "record
  intake" scenario)
- `docs/agent-runs/OIW-705.md`

## Prohibited Paths
- `packages/*`, the three real packs, `apps/`, migrations, lockfile,
  `SESSION.md`, `docs/tasks/`. If the validator/registry treats
  `_template` in a way that breaks the demo selector (it will appear as a
  fourth pack!), flag it: the template must NOT appear on /demo — check

  mechanism or mark BLOCKED requesting one (do not edit the SDK yourself).

## Functional Requirements
1. Guide sections: pack anatomy (file-by-file against contracts v1.5);
   authoring order that avoids the historical defect classes (schemas →
   event definitions with discriminators → fixtures → checksum-keyed
   extractions → gold → rules/workflows/dashboards); the checksum workflow
   (sha256, byte-identical duplicates); validation loop
   (`pnpm validate:packs`, common lifecycle test); the neutrality rules
   (labels-only vocabulary, §10.2); a troubleshooting table mapping the
   real validator errors to causes.
2. Template pack per Owned Paths; every file commented with WHY, not just
   what.
3. Verification: `pnpm validate:packs` shows the template loading valid
   (or the documented exclusion behaviour); common lifecycle test outcome
   for the template documented (passes, or documented why it is excluded).
4. Guide cross-links UX_SPEC/DEMO_SCRIPT where pack content surfaces in UI.

## Non-Goals
No CLI scaffolder (template is the PRD-permitted alternative). No SDK
changes. No fourth demo scenario.

## Acceptance Criteria
- A contributor could produce a valid new pack following only the guide +
  template (the guide's checklist is complete against validator rules).
- `pnpm validate:packs && pnpm test && pnpm lint && pnpm build` pass;
  /demo still shows exactly three packs; CI green.

## Required Commands
`pnpm lint && pnpm test && pnpm build && pnpm validate:packs`
