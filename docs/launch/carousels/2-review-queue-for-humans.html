What a review queue should show a human

An extracted answer is not enough. These are the pieces one review item carries so a person can accept it, correct it or send it back.

Operations Intelligence Workbench1 / 9

Show the source, not a summary

The reviewer sees the original chat message with the exact words behind the value underlined. They read the sentence itself, not a paraphrase.

Operations Intelligence Workbench2 / 9

Show the value as extracted

Field: previous-repair-reference. Value: "brake work done in spring". The reviewer can judge whether the value really follows from the highlighted words.

Operations Intelligence Workbench3 / 9

Show confidence as a number

This item shows 70%. In this demo that figure is authored fixture data, not a measured model score. A real model's confidence would need calibrating first.

Operations Intelligence Workbench4 / 9

Show which extractor produced it

Extractor identity and version are on the item: fixture-intelligence-provider@1.0.0. If a result is wrong later, you know what produced it.

Operations Intelligence Workbench5 / 9

Show status and what it is linked to

Status: pending review. Linked entity: none. The reviewer can see the value is not yet attached to any asset, case or event.

Operations Intelligence Workbench6 / 9

Offer more than accept and reject

Accept, Correct, Reject, Mark insufficient evidence, Link entity, Create entity, Add reviewer note. "The evidence is not enough" is a valid outcome.

Operations Intelligence Workbench7 / 9

Leave an audit entry

Accepting appends an audit entry. In the recorded case: pending to accepted, and one "observation accepted" entry.

Audit view: each entry shows actor, subject and timestamp.
Operations Intelligence Workbench8 / 9

What this does not show

Fixture data, a scripted review, no live model. The layout is the claim, not the accuracy. In this demo, the one vague 70% item is what reached the queue.
