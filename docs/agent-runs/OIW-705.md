## Blocker

**No existing mechanism excludes `scenario-packs/_template/` from
`buildPackRegistry`'s enumeration, and adding one requires editing a
Prohibited Path.**

The task packet anticipated this exact risk ("If the validator/registry
treats `_template` in a way that breaks the demo selector ... flag it
... either rely on an existing exclusion mechanism or mark BLOCKED
requesting one (do not edit the SDK yourself)"). I looked for an existing
mechanism before concluding there isn't one:

- `packages/scenario-sdk/src/registry.ts`'s `buildPackRegistry` calls
  `readdir(scenarioPacksDirectory, {withFileTypes: true})` and filters
  only `entry.isDirectory()` — no name pattern, no dot/underscore-prefix
  skip, no denylist parameter, no environment variable.
- `packages/scenario-sdk/src/loader.ts`'s `loadPackFromDirectory` has
  exactly two non-`loaded` outcomes: `invalid` (no `manifest.yaml` and no
  `narrative/`, or a schema failure) and `skipped` (a `narrative/`-only,
  pre-OIW-004b pack with no `manifest.yaml` at all). There is no
  manifest field (e.g. an `internal`/`template`/`demo: false` flag) that
  produces a distinct, filterable status — a pack either fully loads or
  it doesn't.
- I confirmed, rather than assumed, that every one of these three
  possible states breaks the same test regardless of which one
  `_template` ends up in:
  `packages/application/test/common-lifecycle.integration.test.ts:89-95`
  asserts `registry.invalid` is `[]`, `registry.skipped` is `[]`, **and**
  `registry.loaded` is exactly the three real pack ids, in one
  `beforeAll`. A `_template` that loads valid (what actually happens, per
  the `pnpm test` evidence above) fails the third assertion; had it
  instead been `invalid` it would fail the first; had it been `skipped`
  (e.g. by deliberately omitting `manifest.yaml`, which would also
  contradict this task's own "must LOAD as a valid pack" requirement) it
  would fail the second.
- `apps/web/src/lib/server/pack-registry.ts` (`findPackEntry`,
  `getWorkspacePackLabels`) and the server actions that call it
  (`apps/web/src/app/demo/[pack]/actions.ts`'s `startGuestWorkspace`,
  `apps/web/src/app/w/[workspace]/actions.ts`) also resolve any `packId`
  string against the live registry with no allowlist — today this is
  masked for the Scenario Selector UI by `stubPacks` not including
  `template`, but a direct call to the `startGuestWorkspace` server
  action with `packId: "template"` would not be.

Both files that would need to change to add a real exclusion mechanism
are outside this task's Owned Paths and inside its explicit Prohibited
Paths: `packages/scenario-sdk` (the registry/loader itself — and the
task packet explicitly says "do not edit the SDK yourself") and
`packages/application/test/common-lifecycle.integration.test.ts` (which
is under the blanket-prohibited `packages/*`). I did not edit either.

**Requested resolution** (for whichever track owns `packages/scenario-sdk`
per `PLAN_AMENDMENTS.md` A8/A9 — the core/Codex track): add a documented,
minimal exclusion convention to `buildPackRegistry`, for example (in
order of how invasive each is):
1. Skip directory names starting with `_` during enumeration (the
   convention this task's own Owned Paths already leans on by naming the
   scaffold `_template`, and one shared by other tooling — e.g. `_`-
   prefixed directories are a common "not a real entry" convention).
2. An explicit `excludeDirectories?: string[]` (or similar) parameter to
   `buildPackRegistry`, with the demo/CI callers passing `["_template"]`.
3. A manifest-level opt-out (e.g. `internal: true` on
   `ScenarioPackManifestSchema`) that `buildPackRegistry` filters into a
   fourth, distinct registry bucket.

Any of these would also need
`packages/application/test/common-lifecycle.integration.test.ts` to keep
calling `buildPackRegistry` the same way (options 1/3) or to pass the new
exclusion argument (option 2) — a one-line change either way. Once
either lands, `scenario-packs/_template/`'s own content requires no
further change; re-run `pnpm test` to confirm.

## Architectural decisions
- **Fixtures**: only `smoke/` has on-disk content (2 fixtures), matching
  the Owned Paths' "2 smoke fixtures" instruction; `manifest.yaml` still
  declares all three `fixtures.{smoke,demo,edgeCases}` paths (required by
  `ScenarioPackManifestSchema`), and the missing `demo`/`edge-cases`
  directories surface as the two warnings shown above rather than errors
  — the same tolerance the three real packs relied on before OIW-004b.
- **"one rule per rule file type"** (Owned Paths) was read as: mirror the
  real packs' three-file convention (`severity.rules.json`,
  `escalation.rules.json`, `approval.rules.json`) with exactly one rule
  definition per file, rather than one rule per `RuleAction.type`. To
  still demonstrate the full `RuleAction` vocabulary (Functional
  Requirement framing implies the guide should teach it) within that
  constraint, each of the three rules' `then` array uses more than one
  action type where the real packs do the same (e.g. asset-reliability's
  `missing-inspection-escalation` pairs `create-signal` +
  `create-action`) — across the three files this covers all five action
  types (`create-signal`; `create-case` + `create-action`;
  `propose-decision` + `flag-review`).
- **occurredAt fallback, not a date Observation.** The template's single
  Observation (`template-record-identifier`) is a plain string identifier
  with no date semantics, so the Event definition uses
  `occurredAt: {observationSchemaKey: null, fallback:
  "artifact-received-at"}` rather than inventing a second Observation
  only to satisfy the mapping — keeping the Owned Paths' "one
  entity/observation/event/case schema each" literal while still
  exercising both `occurredAt` mapping modes across the repository (the
  three real packs all use the Observation-keyed mode; this template is
  the one example of the fallback mode).
- **No `tours` field.** Contracts v1.5 makes `ScenarioPackManifestSchema.tours`
  `.optional()` (unlike the v1.1 state `docs/agent-runs/OIW-004b.md`
  worked around), so the template's manifest simply omits it — no
  placeholder or deviation note needed, unlike the three real packs'
  now-resolved v1.1-era workaround.
- **Extraction offsets computed programmatically, not hand-typed** — a
  short Python snippet located each fixture's `SUB-00N` substring by
  `str.index()` and hashed the real file bytes for `sha256`, per §4 of
  the guide's own checksum-workflow lesson (the OIW-004b defect class).
