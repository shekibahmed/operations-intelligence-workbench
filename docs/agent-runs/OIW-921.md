## Architectural decisions
- Engine semantics confirmed by test, not only by reading: `related-event-count >= 2` means two events
  OTHER than the trigger, on a shared entity, within 1440 h up to the trigger time. One other event does
  not match; an event outside the window or on another entity is not counted. The test uses a neutral
  synthetic rule shape in `packages/rules`, with no pack IDs.
- Version choice for the eventual description-only edit: keep `version` at `1.0.0`.

## Blocker

The documented refresh sequence is:
1. Commit the description edit and any test change.
2. Set `sources.json` `sourceRevision` (historical evidence revision) to that commit, update the frozen
   `approval-rule` text and sha256 in `sources.json` (the capture preflight requires the live file to
   equal the frozen text, and the frozen text to equal `git show <sourceRevision>:<path>`). Commit.
3. Run `CASEBOOK_ADMIN_DATABASE_URL=<isolated admin URL> pnpm casebook:capture` on the clean tree.
4. Review the new `recording.json`, run `pnpm casebook:build` and `pnpm casebook:check`, and commit the
   recording, HTML and test expectations together.

This cannot be done inside the packet's ownership for three reasons, each needing a lead decision:

1. `recording.json` is not an Owned Path, yet any `sources.json` edit makes `loadCasebook` fail with
   "Capture input checksum mismatch: scenario-packs/asset-reliability/casebook/sources.json" until a
   fresh capture rewrites `recording.json`. The packet's Prohibited Paths also say to STOP and report
   BLOCKED if the refresh path requires a re-capture that changes the hash-pinned capture inputs.
2. Pre-existing drift: `recording.json` pins `scripts/casebook/capture.ts` at sha256
   `e17bb37ba585...` (that is what `git show 2360e1e:scripts/casebook/capture.ts` hashes to), but the
   file on main and on this branch hashes to `9f6e135f7529...` (changed by the OIW-908 squash merge).
   `pnpm casebook:check` does not compare harness hashes, so it does not report this. Any fresh capture
   will re-pin it, which is a prohibited-path change by the packet's wording and should be an explicit
   decision rather than a side effect.
3. Test pins outside Owned Paths: `scripts/casebook/evidence.test.ts` (lines 82, 86, 88) hard-codes the
   captured revision `2360e1e12c9e70f446957ba4e0b95c78f823dbb2` and the frozen evidence revision
   `d39191038fbe626e6afdd4a54b3a87d2e98cb0e9`; browser tests under `apps/web` may as well. A new
   capture changes both, and the README requires reviewing those expectations deliberately.

A policy question also remains: a new capture replaces the recorded UI run (new `capturedAt`,
timestamps, ids) with a new synthetic run, i.e. the "historical" casebook is regenerated for a wording
fix. AC3 asks the casebook's qualification text to disclose a refresh if the path supports it.
