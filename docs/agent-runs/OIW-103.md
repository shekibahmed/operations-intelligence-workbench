## Architectural decisions
- **`LoadedScenarioPack` is an SDK-owned type, not a contracts type.**
  `@oiw/contracts` only defines `ScenarioPack` as the parsed *manifest*
  (`ScenarioPackSchema = ScenarioPackManifestSchema`); it does not define a
  "fully resolved pack" shape. Since contracts are frozen, the loader
  produces its own `LoadedScenarioPack { directory, manifest, labels,
  workflows, rules, dashboards }`, where `manifest` is exactly the
  contracts-typed `ScenarioPack` and the rest is SDK-validated resolved
  content. This satisfies FR1's "typed ScenarioPack" without touching
  contracts.
- **Dashboard file schema is SDK-owned.** Contracts' `DashboardReferencesSchema`
  only types the manifest's *paths* to dashboard files (A5), not their
  contents. `dashboards.ts` defines `DashboardDefinitionSchema` (id, title,
  widgets) using contracts' `DashboardWidgetTypeSchema` for the widget
  `type` enum, so the fixed 8-type catalogue is still the single source of
  truth.
- **Rule file shape.** A rule file (`manifest.rules[]`) is a non-empty JSON
  array of `RuleDefinition` (`RuleFileSchema = z.array(RuleDefinitionSchema).min(1)`).
  Not specified by contracts or the PRD beyond the file being "rules";
  inferred from the `rules/severity.rules.json`-style filenames in PRD
  §11.1 and the plural manifest field.
- **Rule-reference validation splits into two layers.** (1) The closed
  fact catalogue (A2) is enforced for free by parsing against contracts'
  `FactReferenceSchema` — an unknown fact `kind` is a schema-validation
  error. (2) "Rules reference declared event types" (FR2) is a semantic
  check the SDK adds on top: `collectEventTypeReferences` walks a rule's
  `when` condition tree and `validateRuleEventTypes` checks every
  `event-field`/`eventType` and `aggregate.eventType` reference against
  `manifest.eventTypes[].id`.
- **Fixture/extraction cross-check directory convention.** A1 only fixes
  the pattern `fixtures/**/extractions/<artifact-id>.json`; this task
  additionally establishes `fixtures/<set>/artifacts/<artifact-id>.<ext>`
  as the paired artifact location (artifact-id = filename without
  extension). A fixture set directory, or its `artifacts/` subdirectory,
  missing entirely is a **warning** (tolerated per the task packet); an
  artifact present without a matching, checksum-correct extraction file is
  an **error**.
- **Loader never throws for pack-content problems.** IO errors (missing
  file), YAML/JSON parse errors and Zod validation errors are all folded
  into the same `PackIssue[]` result shape (`{ path, message, severity }`),
  so `buildPackRegistry` can enumerate many pack directories and report
  every invalid one without a single bad pack crashing the process (FR3).
- **Manifest-relative paths are echoed as declared (with their `./`
  prefix) in issue paths**, rather than normalized, so an issue path is
  copy-pasteable back into the manifest for a human fixing the pack.

## Assumptions and deviations
- PRD §11.2's "illustrative manifest" (inline `labels:` object, `packVersion`
  field, `demo:` block) is superseded by the frozen `ScenarioPackManifestSchema`
  in `packages/contracts/src/configuration.ts` (`schemaVersion`, `labels` as
  a path, explicit `fixtures`/`evaluationSets`/`tours`/`defaultLens`/
  `defaultFixtureSet` fields). Per the task instructions, contracts are
  authoritative and frozen; the loader targets the contracts schema, not
  the PRD's older illustration.
- "Schema validation" (PRD §11.3) for `entityTypes[].schema`,
  `eventTypes[].schema`, `observationSchemas[]` and `caseDefinitions[]` is
  implemented as existence + valid-JSON checks only. Contracts do not
  define a JSON-Schema-of-JSON-Schemas contract for these files, and
  authoring their content is explicitly out of scope for this task
  (OIW-004b). Going further (e.g. validating them as JSON Schema
  documents) would invent a contract this task doesn't own.
- `tours[*]` and `evaluationSets[]` are validated the same way (exist +
  valid JSON) even though FR1's parenthetical list ("labels, schemas,
  workflows, rules, dashboards") doesn't name them explicitly; the manifest
  schema requires them, so an unreadable/malformed referenced file is
  still treated as pack-breaking.
- The five required invalid-fixture failure modes map to fixture pack
  directories as: `invalid-manifest` (bad manifest), `invalid-unknown-fact`
  (fact `kind` outside the closed catalogue), `invalid-workflow-state`
  (undeclared workflow state), `invalid-widget-type` (unknown widget
  type), `invalid-missing-extraction` (missing expected extraction). A
  sixth pack, `invalid-unknown-event-type`, was added beyond the required
  five to exercise the semantic "declared event types" half of
  rule-reference validation (distinct from the schema-level "unknown fact
  kind" case) end-to-end through the loader, in addition to its direct
  unit tests in `src/rules.test.ts`.
- No contract blocked this task; nothing is BLOCKED.
