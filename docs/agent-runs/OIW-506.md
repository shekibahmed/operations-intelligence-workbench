## Architectural decisions

- Case files needed a runtime contract because the previous SDK discarded
  them after generic JSON parsing. ADR-011 adds a typed catalogue and validates
  every reference before pack activation.
- Cases group deterministically by pack Case type and related Entity. A fired
  triggering Rule creates the Case; later related Events and Signals reconcile
  into it and can only raise severity/priority.
- Operational Action and Decision IDs group by Case plus pack definition so
  repeated qualifying Events and synchronous retry cannot duplicate the same
  assigned work or governance proposal.
- Workflow policy stays pack-owned. The application evaluates guards through
  the existing RuleEvaluator port and never branches on a pack ID, Event type,
  schema key or fixture ID.
- `ApprovalService` is the sole application outcome path. It requires a human
  session identity, writes Approval first to satisfy the DB boundary, then
  updates Decision and Case and appends human-attributed audits.

## Assumptions and deviations

- The task packet called the optional CaseDefinition addition contracts
  “v1.4”. The merged base already documents Event-definition value constraints
  as contracts v1.4 in ADR-010. ADR-011 therefore records CaseDefinition as the
  next additive revision rather than assigning two incompatible meanings to
  v1.4. This is version-label reconciliation only; the pre-authorized additive
  scope is unchanged.
- Session identity is represented by the framework-neutral typed input
  `{ type: "human", id }`; authentication/authorisation remains outside this
  package as ADR-005 specifies.
- Approval insertion and Decision update use the available repository ports in
  the DB-required order. A future transaction port may make the pair atomic;
  no persistence-internal or migration change was needed for this packet.
