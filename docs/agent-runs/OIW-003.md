## Architectural decisions

Several PRD gaps required a concrete, implementable decision. Each is marked
**[Resolved]** inline in `docs/UX_SPEC.md` with rationale; summarised here:

1. **Lens implemented as a persistent query parameter** (`?lens=leadership|
   operations|technical`) on all `/w/[workspace]/*` routes, rather than a
   separate route tree per lens. Rationale: PRD §8.4 requires the lens to
   persist in the URL and requires all lenses to show "the same underlying
   data" with a lens switch never creating "a separate scenario state" — a
   query param satisfies URL persistence while guaranteeing one canonical
   route/state per screen. Flag for OIW-101 (or whichever Wave 1 task owns
   routing): this is a UX-level contract, not yet a routing implementation.

2. **Primary navigation is always fully visible regardless of active lens**;
   the lens changes default panel expansion, copy tone and which nav item is
   highlighted as "home," not which sections are reachable. Rationale: PRD
   §8.4's "public visitors may switch lenses freely" combined with "same
   underlying data" reads more consistently as full reachability with
   presentation differences than as lens-gated navigation, and it is
   simpler to implement/test (one nav component, not three).

3. **`/demo/[pack]` offers two explicit entry actions** — "Start guided
   tour" (→ Inbox, Operations lens, matching PRD §13.2–13.3's actual first
   guided step) and "Explore freely" (→ Overview, Leadership lens, matching
   §19's designation of Overview as the workspace "control tower"). PRD §13
   only describes the guided path; a direct-exploration entry was added
   because the route table implies Overview is a valid, expected landing
   page independent of the tour.
   **Contract need flagged for OIW-001**: whichever task owns workspace
   creation (server action/route) should accept an optional "entry intent"
   (guided vs. free) or simply let the client choose the redirect target
   after creation — no new persisted field is required, this can be a
   client-side navigation choice after workspace creation succeeds.

4. **Breadcrumb root always links to `/overview`**, independent of the
   active lens, since PRD §19 designates only one workspace-home route.

5. **"Adapt this workflow" CTA trigger for its Leadership Overview banner
   variant** is gated on a session-local "visited at least one detail route"
   flag (client-side only, no tracking dependency — analytics/tracking is
   deferred per amendment A7). PRD §14 requires the CTA to exist and be
   clear but does not specify a trigger condition for the contextual banner
   variant (the persistent top-bar CTA has no such gating).

6. **Entity Detail** is used as the screen's name throughout (matching PRD
   §20.6's section title and the task packet's ten named screens), even
   though PRD §19's route table labels the same route "Entity timeline" —
   timeline is one section within Entity Detail, not the screen's name.

7. **Widget catalogue anatomy/configuration surfaces** (§6 of UX_SPEC.md)
   were authored from PRD §8.1's named widget list plus amendment A5's ~8
   fixed types; PRD does not specify each widget's field-level configuration
   surface, so this document is the first specification of that detail and
   should be treated as binding for OIW-1xx dashboard-widget implementation
   work, not merely illustrative.

  where a gap existed, the nearest binding PRD requirement was extended
