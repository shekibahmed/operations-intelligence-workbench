## Architectural decisions

- **`TOUR_STEPS_BY_PACK` is the only per-pack switch; the framework itself
  (`TourOverlay`, `sessionStorage` resume, keyboard/focus handling,
  `processFixtureArtifacts`) is unchanged in mechanism.** No second tour
  implementation was built. `beforeNext` was generalised from one hardcoded
  literal string plus one hardcoded fixture-id array to a per-step
  `{ fixtureIds }` payload — a minimal, backward-compatible widening (the
  asset-reliability step list's behaviour is bit-for-bit unchanged; only its
  type shape moved from an implicit external constant to an explicit field).
- **The pinned "process by hand" row is per pack**
  (`tourTargetFixtureId`/`TOUR_TARGET_FIXTURE_IDS`), replacing
  `InboxTable`'s single hardcoded `TOUR_TARGET_FIXTURE_ID` export. No new
  component was needed — `InboxTable` was already pack-agnostic apart from
  that one constant.
- **No pack manifest `demo.tour` field exists**, and adding one would touch
  `scenario-packs/*/manifest.yaml`, outside this task's owned paths
  (`apps/web/` only). `TOUR_STEPS_BY_PACK` in `apps/web` is the "default"
  the task packet anticipated; if a future task wants packs to configure
  their own tour via the manifest, that is a manifest-schema change owned
  by a scenario-pack task, not this one.
- **Chosen review-moment artifact per pack**, determined by which fixture's
  extraction has an Observation below the pack's confidence threshold
  (`0.75`, `packages/intelligence/src/validation.ts`) or an explicit
  `insufficient-evidence` status — the same mechanism that routes
  asset-reliability's `previous-repair-reference` field to review:
  - Process Exceptions: `process-exceptions-demo-002` (QC's confirmation
    record), field `reported-cause` (`insufficient-evidence`, "under
    investigation" — confidence 0.4).
  - Document Assurance: `document-assurance-demo-004` (Nadia's
    clarification email to Vantage's counsel), field `due-date`
    (`insufficient-evidence`, no locked date given — confidence 0.3).
  Neither pack's review-worthy fixture is the chronologically-first demo
  fixture (that's true for asset-reliability only), so both new tours pin
  `demo-001` for the manual **Process** click (matching the "process the
  storyline's source artifact" framing and DEMO_SCRIPT's row-1 convention)
  and use the existing `beforeNext` convenience action to real-process the
  fixture(s) between `demo-001` and the review fixture (just `-002` for
  Process Exceptions; `-002` through `-004` for Document Assurance) before
  navigating to the Review Queue — always in ascending fixture-number order,
  matching `packages/application/test/common-lifecycle.integration.test.ts`'s
  proven processing order. A second `beforeNext` batch, after Accept,
  real-processes the remaining fixtures up to (and including) whichever one
  fires the pack's approval rule (`process-exceptions-demo-009`,
  `document-assurance-demo-011`) — mirroring asset-reliability's existing
  single-batch pattern, just split across two batches because the review
  moment falls earlier than the rule-firing moment in these two packs'
  storylines.
- **Softened Document Assurance's dashboard-update step copy.** The first
  draft claimed "critical signals ... have all updated from the approval",
  copying Asset Reliability's phrasing. Screenshots showed Document
  Assurance's Critical Signals stat genuinely stays `0` before and after
  this approval (a real, honest metric-definition difference between packs
  — this decision's risk is `high`, not flagged as a critical signal by this
  pack's own rules) while Pending Decisions and Open Review Cases do
  reflect it. Copy was corrected to name only what actually changes,
  per UX_SPEC §4's "never fabricates data" rule — this applies to a tour
  step's narrative claims, not only its rendered values.

## Assumptions and deviations

- **A real, non-fabricated causal chain was required for the case/rule/
  decision steps**, not just "point the tour at a route." Investigated with
  a temporary, unpushed/uncommitted scratch Vitest file (deleted before
  finishing — never part of any commit) to confirm the exact fixture
  sequence and event assembly behaviour before writing the final step
  lists and copy.
- **Found and worked around a stale build, not a pack-data defect.**
  `packages/application/dist/` (and other packages' `dist/`) predated
  OIW-701/OIW-703's merged source fixes — `dist/event-assembly.js` had no
  `requiredObservationValues` discriminator logic at all. Under that stale
  build, `document-assurance-demo-011` (the fixture that should fire
  `exception-proposed`) instead matched the looser `clarification-requested`
  definition, and the tour's rule-trace step showed "condition did not
  match." This is exactly what the task packet's `Required Commands` line
  already guards against by listing `pnpm build` before `test:e2e` — running
  it (as prescribed) rebuilt every package's `dist/` and resolved the
  symptom with no pack or application-code change. Recorded here because it
  cost real investigation time and the failure mode (a rule "misfiring" per
  a stale compiled discriminator check) could otherwise look identical to a
  genuine BLOCKED-worthy pack-data gap.
- **No pack-data gap actually blocked a tour step** — the BLOCKED protocol
  was not invoked. Every fixture named in both new step lists was verified
  end-to-end (extraction parity, review routing, event assembly, rule
  firing, case creation, decision proposal, approval) against the rebuilt
  packages, and against the two new Playwright specs.
- **No Non-Goal was crossed**: no pack content was added or edited, no tour
  editor was built, no analytics were added, and the asset-reliability tour
  itself is behaviourally unchanged (its own `north-star.spec.ts` stayed
  green throughout, including the final full 9-spec run).
