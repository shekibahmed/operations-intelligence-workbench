## Architectural decisions

- **Link entity/Create entity/Add reviewer note do not change
  `reviewStatus` and do not advance the queue.** UX_SPEC §5.6 states
  "Completing any action advances to the next queue item automatically."
  Read literally across all seven actions, this would eject the reviewer
  from the item immediately after adding a note or linking an entity —
  before they've actually decided Accept/Correct/Reject/Mark insufficient
  evidence for it. Since `Observation.reviewStatus`'s pending/conflicting
  queue membership (the same `QUEUE_STATUSES` set OIW-406's
  `runReviewAction`/`syncArtifactProcessingStatus` already use) is the
  actual definition of "in the queue," and only Accept/Correct/Reject/Mark
  insufficient evidence change it, this task's three new actions instead
  keep the item selected — mirroring how the pre-existing "View revision
  history" toggle already doesn't advance either. The independent
  `ux-accessibility-reviewer` pass flagged this as a literal spec text
  deviation but assessed the reasoning and its accessibility consequences
  as sound (no disorienting queue jump mid-task); recorded here per
  AGENTS.md as a documented PR-note-level deviation rather than a silent
  one. If the lead disagrees, this is a small, isolated change (drop the
  three actions into `runAction`'s existing advance-and-refocus path).
- **`ObservationRepository.correct` reused for entity linking, unmodified.**
  `correct` already snapshots a revision and marks downstream Events for
  re-evaluation on every call, regardless of which fields actually changed.
  Reusing it for Link entity/Create entity (rather than adding a narrower
  public repository method) means an entity link is retroactively visible
  in `listRevisions`/the history panel and correctly triggers downstream
  re-evaluation once an Event/rules engine exists — consistent with
  OIW-406's Known limitations note that re-evaluation marking is exercised
  but currently a no-op. No `packages/persistence` change was needed or
  made (prohibited path for this task).
- **Create entity's type dropdown is scoped to `manifest.entityTypes`, not
  the broader `labels.entityTypes` map.** Asset Reliability's `labels.json`
  declares four entity types (asset, component, location,
  service-provider), but the pack manifest's schema-bound `entityTypes`
  array — the field the packet's "entity type from pack entity types"
  wording maps onto literally — only lists two (asset, component); the
  other two exist as seed-catalogue-only reference types with no JSON
  Schema of their own (OIW-109). The dropdown offers only the two
  manifest-declared, schema-backed types, consistent with the manifest
  being pack-authored, versioned, contract-bound.
- **Reviewer note's `cause` field carries the note text itself**, rather
  than a fixed template like other actions' `cause` (e.g. "Reviewer
  accepted the proposed value"). `AuditEntry.cause` requires a non-empty
  string and is the field the Audit Explorer prints directly — using the
  actual note text there (rather than only in `data.note`) is what makes
  "notes visible... in the audit explorer" true with zero changes to
  `audit/page.tsx`, which already renders every entry's `cause` verbatim.
- **New entity `status` defaults to `"active"`**, not a pack-specific value
  like the seed catalogue's `"operational"`/`"out-of-service"`. Per
  AGENTS.md's Product Rule, core UI code must not invent or assume pack
  vocabulary; `"active"` is a generic, pack-neutral starting status. Entity
  editing (including status) is an explicit Non-Goal, so this value is
  fixed rather than exposed as a form field.
- **Entity picker is a native radio-button list inside a Radix Dialog**,
  not a custom ARIA combobox/listbox. This matches the existing
  Accept/Correct/Reject "distinct, individually labelled controls, not an
  ambiguous icon row" convention, gets keyboard operability for free from
  native `<input type="radio">` semantics, and reuses the same Radix
  Dialog primitive `ConfirmDialog.tsx` already uses for focus-trap/return
  (UX_SPEC §16.3) rather than introducing a second dialog pattern.

  unchanged), so `ObservationRepository.correct`'s downstream
  re-evaluation marking on a Link entity/Create entity action is exercised
  but currently a no-op in live data.
