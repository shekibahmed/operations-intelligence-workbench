## Architectural decisions

- **`test:contracts`/`test:e2e` treated as real, separate commands.** PRD
  §35 lists them distinctly; §16.6/§21.4 only name `pnpm test`/`pnpm eval`.
  I resolved the discrepancy in favour of §35 (more specific, later-numbered)
  so contract correctness can gate CI without waiting on a browser suite.
  Recorded in `docs/EVALUATION.md` §1 as a note, with an explicit instruction
  for OIW-001 (which owns script wiring) to flag its own agent-run file if it
  diverges — this is a plan decision, not a code change, so it doesn't touch
  OIW-001's owned paths.
- **Split `docs/quality/` into two files** (`ACCESSIBILITY.md`,
  `RELEASE_CHECKLIST.md`) rather than one combined document. The task packet
  names `docs/quality/` (a directory) as the owned path without prescribing
  file layout; accessibility criteria and the release checklist are
  read by different audiences at different times (UI-PR review vs.
  milestone sign-off), so separate files avoid one growing doc serving two
  purposes poorly.
- **Database-level constraint recommendations for audit/approval integrity**
  (`docs/SECURITY.md` §3.7, §3.8) are written as recommendations for the
  migration-owning task (unassigned per `SESSION.md` as of this run), not as
  claims that they exist — flagged explicitly so they aren't lost.
- No new ADR is proposed by this task; it is a documentation-only planning
  task and introduces no architectural change requiring one. Several
  sections (e.g. audit table grant restrictions, approval FK constraint)
  are written as *recommendations* for whichever task owns
  `supabase/migrations/`, not as decisions this task has authority to make.

## Assumptions and deviations

- Written entirely against the PRD/amendments, since OIW-001 (contracts,
  architecture, domain model) has not merged yet in this worktree — no
  `packages/contracts/`, `packages/evals/`, or migrations exist to inspect.
  Package names, interface shapes (`IntelligenceProvider`, `ExtractionResult`)
  and fact-catalogue terminology are taken from PRD §17.4/§17.5 and amendment
  A1/A2 directly. If OIW-001 lands with materially different names/shapes,
  the mapping table in `docs/EVALUATION.md` §3 and threat-model mitigations
  in `docs/SECURITY.md` should be spot-checked against the merged contracts.
- Evidence-span tolerance bands (`docs/EVALUATION.md` §5) are a judgment
  call (±5 characters for character-range evidence; exact match required for
  PDF/CSV/JSON) since the PRD does not specify a numeric tolerance. Recorded
  as an explicit decision with rationale rather than left unspecified.
- Numeric evaluation thresholds (`docs/EVALUATION.md` §4–7: precision ≥0.95,
  recall ≥0.90, abstention recall = 1.0, etc.) are proposed targets, not PRD-
  mandated numbers — the PRD specifies metrics to compute (§21.3) but not
  pass/fail bars. Chosen deliberately high for the fixture-provider path
  (deterministic, authored against gold data) and flagged as such so a
  future evaluation-runner task doesn't mistake them for arbitrary.
- `docs/EVALUATION.md` §3 table rows for FR-110/120/121 read "—" for
  verification method with an explanatory note, rather than inventing a
  premature verification method for functionality amendment A7 explicitly
  defers to Wave 4–5. This is the one item flagged per the task packet's
  "note any requirement you found untestable as specified" instruction: the
  requirement itself is fine, it's simply out of P0 scope, so "untestable"
  here means "not yet applicable," not "impossible to test."
