## Architectural decisions

- **`toActionErrorMessage` rethrows Next's redirect signal (security-review
  fix).** `requireWorkspace(slug)` calls Next's `redirect("/demo")` on an
  invalid/expired ADR-007 session, which works by throwing a special error
  carrying a `NEXT_REDIRECT` digest that must propagate uncaught for Next's
  action runtime to turn into a real HTTP redirect. The first draft of every
  server action added by this task wrapped `requireWorkspace` in a plain
  `try { ... } catch (error) { return { ok:false, message: error.message } }`
  — which silently intercepted that redirect and turned an intended
  "your session expired, go back to `/demo`" navigation into a generic
  failed-action banner exposing the raw `"NEXT_REDIRECT;replace;/demo;307;"`
  string. An independent security-reviewer pass on this diff caught this
  (the codebase already has an `isRedirectError` helper, used by two Wave-1
  client components, that this task's new server actions should have reused
  from the start). Fixed via a shared `toActionErrorMessage` helper
  (`lib/server/action-error.ts`) that every catch block in
  `inbox/actions.ts`/`review/actions.ts` now calls: it rethrows
  `NEXT_REDIRECT` errors, and — closing a related error-message-leakage gap
  the same review raised — only echoes a caught error's own `.message` to
  the client for known, intentionally-informative error types (this
  module's `UserFacingActionError`, and `@oiw/ingestion`/`@oiw/intelligence`'s
  adapter/provider errors, which all carry a `retryable` flag); anything
  else (e.g. an unexpected database error) is logged server-side via
  `console.error` and replaced with a generic message before it reaches the
  client.
- **Technical Inspector's raw viewer highlights evidence spans
  (accessibility-review fix).** UX_SPEC §5.12 requires the raw artifact
  viewer to reuse the Review Queue's evidence-span highlighting; the first
  draft rendered `artifact.rawText` as an unhighlighted block, which an
  independent `ux-accessibility-reviewer` pass flagged against that line of
  the spec. Extracted the `<mark>`-based highlighting into a shared
  `highlightRanges` helper (`lib/highlight-text.tsx`), used by both
  `ReviewQueuePanel` (single selected observation's evidence) and the
  Technical Inspector (every one of the artifact's Observations' evidence
  spans, deliberately scoped to Observations' own evidence segments rather
  than every persisted `ArtifactSegment` — the latter also includes the
  ingestion adapter's coarse parse segments, e.g. one per chat message,
  which would highlight entire message blocks instead of the specific
  phrase an Observation actually cites).
- **Artifact status re-sync on last review resolution.** OIW-301's
  `ArtifactProcessingService` sets `processingStatus: "needs-review"` once,
  at processing time, and nothing in that package re-checks it afterward.
  Left alone, an Inbox row would stay "Needs review" forever even after
  every one of its Observations left the review queue. Since
  `ArtifactRepository.updateProcessingStatus` is part of `@oiw/persistence`'s
  public API, `syncArtifactProcessingStatus` (in `review/actions.ts`) checks
  — after each review action — whether the artifact still has any
  pending/conflicting Observation, and flips it to `processed` if not. This
  is additive to OIW-301's contract, not a change to it, and uses only
  public repository methods.
- **`derivation: "human"` on Correct.** `ObservationSchema`'s `superRefine`
  requires a `"supported"` `evidenceStatus` on a `derivation: "machine"`
  Observation to carry a non-null `evidenceSegmentId`. A correction can
  legitimately have no original evidence segment (e.g. correcting a
  previously insufficient-evidence field). Rather than inventing a synthetic
  evidence segment, `correctObservation` moves `derivation` to `"human"` for
  the corrected value — the original machine extraction, its confidence and
  its extractor identity remain fully readable via
  `getObservationRevisions`/`listRevisions`. Accept, Reject and Mark
  insufficient evidence all leave `derivation` untouched, since none of them
  require this.
- **Corrected value is schema- and type-validated before persistence.**
  `correctObservation` looks up the pack's `ObservationSchemaDefinition` for
  the Observation's `schemaKey`, coerces the reviewer's text input to the
  schema's `valueType` (string/number/boolean/JSON-parsed object), and
  revalidates with `@oiw/scenario-sdk`'s public `validateObservationValue`
  before calling `ObservationRepository.correct` — per AGENTS.md, structured
  output (human or machine) is schema-validated before persistence.
- **"Mark insufficient evidence" and "Correct" both persist with
  `reviewStatus: "corrected"`.** The `Observation.reviewStatus` enum has no
  dedicated "insufficient" state; marking insufficient evidence is, at the
  domain-contract level, a correction of the extracted value to "no value,
  insufficient evidence." Both actions correctly leave the review queue
  (queue lists `pending`/`conflicting` only) and are individually audited
  and labelled distinctly in the UI and in `Badge`/`REVIEW_STATUS_LABEL`.
- **Processing trace is derived from the audit trail, not a persisted
  field.** OIW-301's `ArtifactProcessingResult.processingTrace` (steps,
  `durationMs`) is returned transiently from `processArtifact` and never
  written to a queryable column — `packages/application`/`packages/persistence`
  are prohibited paths for this task, so this couldn't be added upstream.
  The Technical Inspector instead builds its "processing trace" and
  "processing duration" from the real, already-persisted
  `artifact-processing-started`/`-completed`/`-failed`/`extraction-rejected`
  Audit Entries for that artifact — real, non-fabricated data, just sourced
  differently than a literal `processingTrace` object. Flagged below as a
  follow-up for whichever task next touches `packages/application`.
- **`Entities` UI actions (Link entity / Create entity) dropped from the
  Review Queue.** The Wave-1 stub review panel had these buttons per
  UX_SPEC §5.6's full action list, but OIW-406's Non-Goals explicitly
  exclude entity/case screens and there is no entity-resolution engine to
  back them (`Observation.entityId` is always `null`). Implementing them
  would either be non-functional decoration or require inventing backend
  behaviour outside this task's scope, so they're removed rather than
  faked. Accept/Correct/Reject/Mark insufficient evidence and candidate
  selection (Functional Requirement 3's explicit list) are all real.
- **Audit-entry hashing reimplemented locally.** `@oiw/application`'s
  canonical-JSON + SHA-256 audit-hash chain helper (`records.ts`) is not
  re-exported from that package's public `index.ts`. `review/actions.ts`
  needs to construct a valid `AuditEntry` to call the public
  `ObservationRepository.correct(..., auditEntry)`, so
  `src/lib/server/audit.ts` reimplements the same scheme locally (sorted-key
  JSON stringify, SHA-256, `previousEntryHash` chained off the workspace's
  latest entry) so review-action audit entries extend the same
  tamper-evident chain as processing/seed/reset entries.

## Assumptions and deviations

- The packet's "review the ambiguous observation" (Acceptance Criteria) is
  read as the brake-fault artifact's one below-confidence-threshold
  Observation (`previous-repair-reference`, 0.70 < 0.75), not a literal
  `alternativeCandidates` ambiguity — no Asset Reliability demo fixture
  attaches `alternativeCandidates` to this artifact. Candidate selection is
  still fully implemented (`acceptObservation`'s `selection` parameter,
  exercised by a dedicated component test) and will engage on any
  observation that does carry alternatives.
- `packages/application`'s `ArtifactProcessingPackResolver` is satisfied
  with an object that ignores its `workspaceId` argument and always returns
  the already-resolved pack for the current request — correct because the
  workspace's active pack was already resolved once via
  `findPackEntry(workspace.activePackId)` before constructing the service.
- Corrected-value type coercion supports the pack's four `valueType`s
  (`string`/`number`/`boolean`/`object`) via a plain textarea (numbers
  parsed, booleans as `"true"`/`"false"`, objects as JSON text). No richer
  per-type editor (date picker, enum select) was built; every Asset
  Reliability schema currently used by review-eligible fields is `string`,
  so this isn't exercised beyond the string path in the live journey.
- `?state=error` support was kept on the Review Queue page (matching
  Inbox/Technical Inspector's existing pattern) for consistency, though the
  packet didn't call it out explicitly.

## Known limitations / follow-up

- Processing trace/duration is reconstructed from Audit Entries rather than
  a persisted `processingTrace` field (see Architectural decisions) — a
  follow-up task touching `packages/application`/`packages/persistence`
  could persist the real trace object for a more literal technical view.
- Entity resolution remains entirely unimplemented (`entityId` always
  `null`); Link entity/Create entity review actions were intentionally not
  built (Non-Goal).
- Rules/Events/Cases/Decisions engines still don't exist, so an accepted or
  corrected Observation has no downstream Event/Case to actually
  re-evaluate yet — `ObservationRepository.correct`'s re-evaluation marking
  is exercised (no impacted Events exist yet, so it's a no-op in the
  current data), but end-to-end re-evaluation behaviour can't be verified
  until that engine lands.
- Multi-observation-per-artifact review ordering is by `createdAt`; no
  reviewer-configurable sort/filter was added to the queue (not required by
  the packet).
