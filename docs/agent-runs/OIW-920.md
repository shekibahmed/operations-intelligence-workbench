## Item 4 root cause (analytics "event loss")
The event is not lost and the client sender is not at fault (`emitProductAnalyticsEvent` already used `fetch` with `keepalive: true`, so no `sendBeacon` change was made). Evidence: after a failing 8-repeat run, `analytics_events` held 6 sessions containing only `scenario-selected`, 6 sessions containing only `demo-started`, and 2 sessions containing both. Six splits matched the six failures.

Mechanism: the first visit to `/demo/asset-reliability` has no `oiw_analytics_session` cookie. The page's `scenario-selected` POST to `/api/analytics` and the "Start guided tour" server action (which records `demo-started`) both call `getOrCreateAnalyticsSessionId` cookie-less when the test clicks right after hydration. Each mints its own UUID and sets its own cookie. The browser keeps the last one; the test reads that cookie and queries only that session. A human is very unlikely to click within the POST round trip, but the server-side race is real.

Fix: the test now waits for the page's analytics response (202) before starting the tour. The server route contract is unchanged and nothing new is sent to anyone.
