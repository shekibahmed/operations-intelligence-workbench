## Architectural decisions

- **Advancement is triggered from the UI layer, not a new package.** OIW-501
  shipped `ArtifactAdvancementService` but nothing called it. Since
  `apps/web` is the only owned path, `src/lib/server/artifact-advancement.ts`
  wires it the same way `artifact-processing.ts` already wires
  `ArtifactProcessingService` — structural typing over the real
  `@oiw/persistence` repositories, no adapter package needed. It runs after
  Process (when the resulting status is `processed`/`needs-review`) and
  after every Review action that resolves an Observation; `event-assembly.ts`
  only composes Observations already in a composable review state, so
  calling it eagerly is safe and idempotent even when other Observations on
  the same Artifact are still pending.
- **Decision approve/reject is implemented directly against
  `@oiw/persistence`, not deferred as an integration point.** The task
  packet's integration-point language is about the rule engine's
  `create-case`/`create-action`/`propose-decision` executors (OIW-506's
  job — deciding *what* Case/Decision to create). Once a Decision exists,
  acting on it (recording a human Approval and transitioning its status) is
  a UI-and-persistence concern with no dependency on OIW-506, and
  `@oiw/persistence` already enforces the approval-before-approved
  invariant — so this is real, not stubbed, and will work unchanged once
  OIW-506 starts creating real Decisions.
- **Closure requirements use two generic heuristics instead of a hardcoded
  label/requirement table.** The previous stub hardcoded three
  asset-reliability-specific requirement IDs with English labels and
  bespoke completion logic. `packages/contracts`' `CaseSchema
  .closureRequirementIds` is a free-text pack slug with no completion
  contract at all. `isRequirementComplete` (`src/lib/case-detail.ts`) uses
  two pack-neutral rules: a requirement named after an Event type is
  satisfied once that Event type appears in the Case's timeline; a
  requirement mentioning "decision" is satisfied once every Decision on the
  Case is resolved (approved/rejected). Labels are humanized from the slug
  (`inspection-completed` → "Inspection Completed") rather than a
  hardcoded table, per AGENTS.md's Product Rule (no pack vocabulary baked
  into core/UI code). This is a heuristic, not a contract — flagged below
  and a reasonable candidate for a future contract addition
  (`ClosureRequirementDefinition` in the pack manifest) if precision here
  ever matters for a real customer.
- **Rule trace correlates outcomes to Audit Entries by structural
  convention, not a new field.** `RuleDefinition`/`Decision` carry no
  "which rule proposed this" back-reference. `rule-trace.ts` matches a fired
  action to its real persisted effect by subject/data correlation already
  present in OIW-501's audit shape (`rule-review-flagged`/
  `rule-action-pending` share `subject.id` with the triggering
  `rule-evaluated` entry; `signal-created` shares `ruleId`/`ruleVersion` and
  has the triggering event in its `eventIds`). Decision Centre's
  "triggering rule" link uses the same generic convention
  (`subject.type === "decision" && data.ruleId` present) so it will start
  working the moment OIW-506 records that Audit Entry shape when it creates
  a Decision — no OIW-509 code change needed.
- **Rule trace links omit `?event=`.** Signal.eventIds is a sorted,
  deduplicated set (current + all contributing related events, per
  OIW-501), so `eventIds[0]` is not reliably the specific event whose
  `rule-evaluated` entry produced that Signal. Rather than risk showing a
  stale/unrelated (possibly not-fired) evaluation, every in-app link to a
  Rule trace omits the event and lets `buildRuleTraceView` default to "the
  most recent evaluation of this rule that actually fired" — correct rule
  identity/mechanism, at the cost of not always being the exact execution
  instance. The route still accepts an explicit `?event=` for a caller that
  does know it.

## Assumptions and deviations

- **`create-case`/`create-action`/`propose-decision` stay unactioned** —
  exactly per the task packet's anticipated integration point. Verified
  empirically (see Tests) that the seeded `asset-reliability` demo fixture
  set, once fully processed, produces 0 real Cases/Decisions and 11
  `rule-action-pending` outcomes. Case List and Decision Centre are fully
  wired and will show data the moment OIW-506 supplies real rows; no
  reconciliation code change should be needed on this side, only OIW-506's
  executor.
- **Removed a broader "process the whole 25-artifact demo fixture set and
  show a real fired Rule trace / repeated-pattern Signal" Playwright test.**
  Empirically, clicking "Process" for 25 Inbox rows in quick succession
  raced the Inbox table's `router.refresh()` (a full Server Component
  re-render after each action) — one row's click was intermittently
  dropped, so the resulting dataset was smaller and less predictable than a
  human clicking through the demo at a normal pace. Chasing this into a
  fully robust bulk-click e2e test was judged not worth the fragility for a
  test beyond what the task packet requires (it only asks to "walk entity
  timeline" after review acceptance, which the single-artifact journey does
  deterministically). The richer, multi-rule, multi-Signal scenario is
  instead covered by `rule-trace.test.ts`'s realistic fixtures. This
  `router.refresh()` race is a pre-existing Inbox behaviour (OIW-406, not
  touched by this task) that only shows up under rapid, scripted, many-row
  clicking; flagged here in case a future bulk-operations task hits it.
- **No case-detail screenshot.** The prior stub-era `case-detail-*.png`
  screenshots are removed rather than kept stale, since no real Case exists
  to screenshot yet (Case List's real empty state is screenshotted
  instead). The lead should regenerate a populated Case Detail screenshot
  once OIW-506 creates real Cases.
- **`nav-defaults.ts`'s `DEFAULT_ARTIFACT_ID`/`DEFAULT_RULE_ID`** (the
  Technical nav submenu's generic Artifacts/Rules targets) remain the
  pre-existing stub UUIDs from OIW-201/406 and will 404 against any real
  workspace exactly as they already did before this task — a pre-existing
  shell gap (no route exists to redirect "Technical > Rules" to *a* real
  rule without picking one), not something this task's functional
  requirements cover. Left unchanged rather than scope-creeping into shell
  navigation.
- **Action-item completion and case notes were implemented as real,
  audited actions** (`cases/[caseId]/actions.ts`) even though the task
  packet's functional requirements only named these as Case Detail
  *sections* to render, because UX_SPEC §5.8 explicitly lists
  "add/complete action item" and "add case note" as this screen's Actions,
  and the write path was a small, self-contained addition using only
  existing repository methods.

## Known limitations / follow-up

- Case List / Decision Centre render real, correct, but empty data against
  the current seeded packs, pending OIW-506's case/decision engine.
- The closure-requirement completion heuristic (`isRequirementComplete`) is
  a reasonable generic approximation, not a contract-backed rule; if a pack
  ever needs a closure requirement that isn't "named after an Event type"
  or "about a Decision", it will show as unsatisfied by default rather than
  guessing. A future `ClosureRequirementDefinition` in the pack manifest
  (mirroring `EventDefinition`/`RuleDefinition`) would remove the
  heuristic.
- Rule trace links resolve to "the most recent fired evaluation of this
  rule" rather than "the exact evaluation that produced this specific
  Signal/outcome" (see Architectural decisions) — correct mechanism, not
  always the exact instance.
- The pre-existing `nav-defaults.ts` stub-ID nav targets (Technical >
  Artifacts/Rules) and the Inbox's `router.refresh()` bulk-click race are
  both pre-existing, out-of-scope observations from this task's testing,
  not regressions it introduced.
