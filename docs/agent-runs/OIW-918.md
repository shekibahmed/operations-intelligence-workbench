## Findings for the lead

1. **Rule description is wrong and cannot be fixed inside this packet.** The
   engine's related-event aggregate excludes the triggering event
   (`packages/rules/src/engine.ts`, `relatedEvents`: `event.id ===
   context.event.id` is skipped), so `>= 2` means two other events. The
   description saying "at least one other related event" understates this.
   Editing the description makes `scripts/casebook/capture-lifecycle.test.ts`
   fail (18 tests, "Intentional source refresh required: approval-rule")
   because `scenario-packs/asset-reliability/casebook/sources.json` snapshots
   the rule file text and the generated casebook HTML embeds it. Casebook
   files are prohibited for this task, so I reverted the edit. Fix: a
   follow-up that changes the description to "at least two other related
   events (the triggering event is not counted)" and refreshes the casebook
   sources intentionally. The casebook narrative (`case.json`) already says
   "at least two related events".
2. **Database-level gaps on Approvals (real, open, need a migration).**
   Verified with raw SQL in `approval-governance.test.ts`: (1) no `CHECK` on
   `approver` content, an empty-string approver row is accepted; (2) that
   `approved` row satisfies `decisions_require_human_approval`, which checks
   existence/outcome/Decision, not human identity, so a Decision can be approved
   with no human identity by a writer with `approvals` access; (3) `approvals`
   is not append-only, so `UPDATE approvals SET decision_id` re-points an
   Approval at another Decision and then Y can be approved; (4) `DELETE FROM
   approvals` is accepted. The earlier version of this run recorded these as
   passing characterisation tests and treated a "privileged writer" as a
   separate threat model. That was wrong: the application's own database role
   can run the same SQL, and the packet says an exposed bypass must be
   reported, not enshrined. The tests are now four `it.fails` known-gap
   markers that state the secure behaviour (they pass only while the gap
   exists and start failing when a migration closes it), and claim (a)/(b) are
   marked still false at the database layer. Recommended migration: `CHECK
   (btrim(approver) <> '')` and a BEFORE UPDATE OR DELETE trigger on
   `approvals`, then change the four `it.fails` to `it`. Lead decision needed:
   land the migration, or accept the threat model in writing.
3. The README must not say "the database rejects an empty approver" or that an
   Approval for X cannot authorise Y "by the database"; say the application
   and contract layers reject empty approvers, and that the database trigger
   guards direct Decision status writes only.
4. **Wording to use for claim (e)** (README line and ARCHITECTURE.md line 50 are
   outside this packet's owned paths and still say "compiles with any one pack
   directory removed", which overstates): "`pnpm architecture:check` confirms no
   TypeScript project in the repository compiles any Scenario Pack file and that
   the pack registry still loads every other pack when any one pack directory is
   removed." The lead should apply it to README.md and docs/ARCHITECTURE.md.
5. README scope: the scan covers every directory under `packages/` (discovered,
   not a hand list), non-test sources only, not `apps/web`. Say "every package
   under `packages/`" rather than listing names.

## Architectural decisions
- Neutrality is proven as a compile closure (resolved imports, no type
  check) of each tsconfig plus a runtime registry test, rather than by
  deleting directories from the working tree, so the check is side-effect
  free and runs in CI in about 8 seconds.
- The directory list for the industry-term scan is now every directory under
  `packages/` (previously a hand list that omitted `scenario-sdk`, `ui` and
  `test-support`). All three were already clean.
- Hostile-provider tests substitute an `extract()` implementation but run the
  real `ArtifactProcessingService`, validator, abstention policy,
  advancement service, rule engine and Postgres repositories.

## Assumptions and deviations
- The packet allowed a description fix "only if the count excludes the
  trigger". It does, but the edit is blocked by the casebook snapshot, so no
  edit was made (deviation, explained above).
- `tests/security/architecture-neutrality.test.ts` runs the full check in
  process once (about 8 s) in addition to the CLI in CI.
- Test files import `packages/*/src` by relative path, as the existing
  security tests do; `@oiw/contracts` runtime imports are not aliased in the
  security vitest config.

## Dependency requests
