## Findings for the lead

1. **Rule description is wrong and cannot be fixed inside this packet.** The
   engine's related-event aggregate excludes the triggering event
   (`packages/rules/src/engine.ts`, `relatedEvents`: `event.id ===
   context.event.id` is skipped), so `>= 2` means two other events. The
   description saying "at least one other related event" understates this.
   Editing the description makes `scripts/casebook/capture-lifecycle.test.ts`
   fail (18 tests, "Intentional source refresh required: approval-rule")
   because `scenario-packs/asset-reliability/casebook/sources.json` snapshots
   the rule file text and the generated casebook HTML embeds it. Casebook
   files are prohibited for this task, so I reverted the edit. Fix: a
   follow-up that changes the description to "at least two other related
   events (the triggering event is not counted)" and refreshes the casebook
   sources intentionally. The casebook narrative (`case.json`) already says
   "at least two related events".
2. **Database-level limits on Approvals (not application bypasses).**
   Characterisation tests in `approval-governance.test.ts` pin that the
   `approvals` table has no `CHECK` on `approver` content (a raw
   empty-string approver row is accepted) and is not append-only (a writer
   with direct database privileges can re-point an Approval at another
   Decision and then approve that Decision, or delete an Approval after the
   Decision was approved, because the trigger fires only when a Decision row
   is written). The application exposes no path to either, so I did not
   classify this as a bypass of the README claims, and migrations are
   prohibited here. Recommended follow-up migration: `CHECK
   (btrim(approver) <> '')` and an append-only trigger on `approvals`, then
   invert the two characterisation tests. The SECURITY.md disposition states
   these limits in the open rather than claiming a database guarantee.
3. The README claim should not say "the database rejects an empty
   approver"; say the application and contract layers do.

## Architectural decisions
- Neutrality is proven as a compile closure (resolved imports, no type
  check) of each tsconfig plus a runtime registry test, rather than by
  deleting directories from the working tree, so the check is side-effect
  free and runs in CI in about 8 seconds.
- The directory list for the industry-term scan is now every directory under
  `packages/` (previously a hand list that omitted `scenario-sdk`, `ui` and
  `test-support`). All three were already clean.
- Hostile-provider tests substitute an `extract()` implementation but run the
  real `ArtifactProcessingService`, validator, abstention policy,
  advancement service, rule engine and Postgres repositories.

## Assumptions and deviations
- The packet allowed a description fix "only if the count excludes the
  trigger". It does, but the edit is blocked by the casebook snapshot, so no
  edit was made (deviation, explained above).
- `tests/security/architecture-neutrality.test.ts` runs the full check in
  process once (about 8 s) in addition to the CLI in CI.
- Test files import `packages/*/src` by relative path, as the existing
  security tests do; `@oiw/contracts` runtime imports are not aliased in the
  security vitest config.
