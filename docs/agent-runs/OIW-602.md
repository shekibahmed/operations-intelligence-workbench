## Architectural decisions

- **`lib/server/metrics.ts` is the sole, explicitly marked OIW-601
  integration point**, per the task packet's instruction. Every caller
  (`overview/page.tsx`, `DashboardGrid`) depends only on the exported
  `MetricValue`/`evaluateMetrics(packEntry, repositories, workspaceId, base,
  labels)` shape; the lead can replace the function body with a call into
  the real `@oiw/application` service without touching any other file. The
  adapter deliberately mirrors OIW-601's own task packet (same seven
  aggregation kinds, same `MetricDefinition` contract already frozen in
  `@oiw/contracts`) so the swap is a like-for-like replacement, not a
  redesign.
- **`count-records`/`count-by-field` return both a number and bounded real
  sample records.** UX_SPEC's widget catalogue pairs some widgets
  (list-card, pending-approvals) with metrics whose declared A5 aggregation
  kind is a bare count (e.g. `assets-awaiting-approval` is `count-records`,
  but the Pending-approvals card needs an actual list per §6.6). Rather than
  special-casing those two widget types against the metric's declared
  parameters a second time, `evaluateCountRecords` computes both the count
  and up to 5 real, sorted, linked sample records once; `stat-card` uses the
  count, `list-card`/`pending-approvals` use the records. This is a
  synthesis the metric contract's aggregation-kind vocabulary doesn't
  literally specify, so it's called out here for OIW-601's author to
  confirm or diverge from when the real service replaces this file.
- **The tour drives its own real batch-processing step, not just
  navigation.** DEMO_SCRIPT's steps 2–3 read as "process the one informal
  message," but the pack's real rule conditions (`related-event-count >= 2`
  for the repeat-fault signal; a safety-critical indicator for the
  hold-from-service decision) need the four other related fixture artifacts
  processed too (confirmed against `docs/agent-runs/OIW-506.md`'s own proven
  processing order). Rather than changing the visitor-facing narrative or
  silently faking the resulting Case/Decision, `processFixtureArtifacts`
  runs the exact same real `processArtifactForWorkspace`/`tryAdvanceArtifact`
  path a manual Inbox click uses, for four specific, stably-identified
  fixture artifacts, triggered from the tour's own Next button right after
  the visitor accepts the one review item that is genuinely part of the
  visible narrative. Order independence (does it matter that the visitor's
  own artifact is processed before the batch, not interleaved as OIW-506's
  test proved?) was verified against `case-lifecycle.ts`'s `ensureCasesForRule`
  / `relatedCase` design, which resolves-or-creates the Case for any rule
  bound to the same `CaseDefinition.triggeredByRules` regardless of firing
  order — then confirmed empirically via the north-star e2e test.
- **Tour target selectors are plain CSS selectors, not only
  `data-tour="..."`.** Initially every step spotlighted a `data-tour`
  attribute exclusively; the Leadership dashboard's "reflects the approval"
  step originally spotlighted the entire (very tall) dashboard grid, which
  looked wrong in a tablet screenshot (a highlight ring stretching the full
  page height). Retargeted that one step at `StatCard`'s own
  `aria-labelledby="stat-critical-signals"` — a real accessibility
  attribute already on the DOM, not new markup — by generalizing
  `TourStep.target` to hold any CSS selector. `data-tour` remains the
  convention for the other nine steps.
- **`resolveOutcomes` correlation, not a new contract field.** Same
  structural-audit-correlation pattern OIW-509 established for the
  `create-signal`/`flag-review` branches: `case-created`/
  `action-item-created` match on `data.ruleId` + `data.eventId` (both
  present on those audit entries); `decision-proposed` matches on
  `data.ruleId` alone (no `eventId` field on that entry, since a Decision's
  proposing rule can fire on a different Event than the one that created its
  Case) — acceptable precision at this product's single-small-workspace
  scale, not a many-tenant correctness guarantee.

## Remediation (post-OIW-601 reconciliation)

`main` merged OIW-601 (`@oiw/application`'s real `MetricEvaluationService`,
Metric contract v1.5) after this branch's original cut. OIW-601 normalised
every pack's `dashboards/metrics.json` to the closed v1.5 vocabulary
(`count`, `count-where`, `count-by-field`, `trend-over-time`, `sla-derived`),
renaming and in some cases changing the semantics of the aggregation kinds
this adapter's marked stub reimplemented under their old (pre-v1.5) names.
With `origin/main` merged into this branch (merge commit present; a stray
`git stash` entry from that merge is not part of this work and was left
untouched), `apps/web/src/lib/server/metrics.ts` no longer recognised any
aggregation kind, failing 5 unit tests and 2 e2e assertions. This section
records the reconciliation.

- **`lib/server/metrics.ts` now calls the real `MetricEvaluationService`**
  for every aggregation kind, instead of reimplementing the vocabulary
  against `@oiw/persistence` directly. It also now reads
  `packEntry.pack.metricDefinitions` (a `scenario-sdk`-validated
  `ReadonlyMap<string, MetricDefinitionV15>`, populated by the pack loader
  since OIW-601) instead of re-reading and re-parsing each pack's
  `dashboards/metrics.json` by hand — one less place that could drift from
  the loader's own validation (duplicate-ID rejection, dashboard
  `metricId` cross-checks).
- **The service's results are purely numeric/statistical** (a count, a
  breakdown, a time-series of bucket counts, an SLA bucket-count table, or a
  hypothetical/illustrative marker) — it has no concept of sample titles,
  hrefs, per-item SLA rows or an activity feed. Every widget that needs one
  of those (list-card, pending-approvals, sla-table, activity-feed) has the
  adapter separately re-select the same filtered records straight from
  `@oiw/persistence`, using a small local re-implementation of the service's
  own declarative filter/window matching (documented inline; this is
  presentation-only re-derivation of the same declarative filters, not a
  second copy of business logic).
- **Two v1.5 aggregation kinds are ambiguous between two widget
  presentations that share one `aggregation` value**, and the v1.5 contract
  carries no per-widget intent — only the pack-declared `format` disambiguates,
  so the adapter switches on `format`, not on any metric ID (kept pack-neutral,
  matching `DashboardGrid`'s existing "no pack ID or industry noun" rule):
  - `trend-over-time` + `format: "text"` (e.g. `recent-reliability-activity`)
    renders as the activity feed (UX_SPEC §6.7: a real reverse-chronological
    list with timestamps and summaries), built from real Audit Entries,
    instead of the service's day-bucketed event *count* the aggregation kind
    would otherwise produce — an activity feed is not a chart.
  - `sla-derived` + `format: "duration"` (e.g. `average-time-to-triage`)
    renders as a single stat, not the SLA risk table `sla-derived` normally
    produces. The pack's original "average time between a fault-reported
    event and the first inspection/maintenance-completed event" semantics
    cannot be recovered: the v1.5 `sla-derived` schema has no
    `fromEventType`/`toEventType` parameters (ADR-012: v1.5 deliberately
    excludes arbitrary averages/event-to-event durations). The nearest
    generic, structurally-available substitute — computed from fields the
    metric's own parameters already operate on — is the mean absolute
    distance between "now" and each matching record's own `dueAt`. Flagged
    here for the pack owner: if a literal event-to-event triage duration is
    still wanted, it needs an explicit v1.6 aggregation, not a pack query
    string (per ADR-012's own stated position).
  - `sla-derived` + `format: "number"` (e.g. `overdue-actions`) keeps
    rendering as the SLA table (UX_SPEC §6.5 needs per-row item/due/risk,
    which the aggregate bucket-count result doesn't carry), built from the
    same filtered records using the metric's own `atRiskWithinHours` — an
    improvement over the pre-remediation adapter, which used a hardcoded
    72-hour window instead of the pack-declared threshold.
- **`count-by-field` breakdown ordering**: the service sorts breakdown keys
  alphabetically (locale-independent, deterministic). The adapter re-orders
  by severity rank when every key is a known severity tier (matching the
  pre-remediation and pre-OIW-601 behaviour for "Cases by Severity"),
  otherwise keeps the service's alphabetical order — presentation-only,
  since UX_SPEC §6.2 leaves tier order to the widget.
- **Hypothetical metrics** (`estimated-downtime-exposure`) are unaffected in
  behaviour: still never computed from the metric's own repository access
  (the service structurally forbids it), still scaled from a real, separate,
  closed-vocabulary count (flagged critical/high Signals) by a documented
  illustrative constant. Only the source of the `classification`/`format`
  values moved from the old hand-parsed `MetricDefinition` to the service's
  `MetricEvaluationResult`.
- `apps/web/tests/metrics.test.ts` rewritten: one behavioral test per v1.5
  aggregation kind (`count-where`, `count-by-field`, `sla-derived` ×2 format
  branches, `trend-over-time`/activity, `count`+hypothetical), evaluated
  against the pack's real, `scenario-sdk`-loaded `metricDefinitions` (via
  `buildPackRegistry`, replacing the previous hand-built `PackRegistryEntry`
  fixture that predated `metricDefinitions` existing on the loaded pack).
  The new `sla-derived`+`duration` test asserts within a small tolerance
  window (real wall-clock `Date.now()` vs. a fixed `dueAt`), matching how
  the pre-existing SLA-row test already tolerated real-clock evaluation.
